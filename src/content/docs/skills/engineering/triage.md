# Triage

让项目 issue tracker 上的 issue 走过一个小的 **triage 角色状态机**。

如果这个仓库把**外部 pull request** 当成一个请求入口（见 issue-tracker 配置），
triage 也覆盖它们：**一个 PR 就是"带代码的 issue"**，
用同样的角色、同样的状态、同样的状态机，
只有下面标着"**对 PR**"的几处差异。把裸写的 `#42` 按 tracker 配置解析成 issue 或 PR。

**triage 期间发到 issue tracker 的每一条评论或 issue，都必须**以这句声明开头：

```
> *This was generated by AI during triage.*
```

## 角色

两个**分类（category）**角色：

- `bug`：有东西坏了
- `enhancement`：新功能或改进

五个**状态（state）**角色：

- `needs-triage`：维护者需要评估
- `needs-info`：等报告人补充信息
- `ready-for-agent`：已充分规格化，可交给 AFK agent
- `ready-for-human`：需要人来实现
- `wontfix`：不会被处理

**对 PR 而言**，同样的状态是相对附带的代码来读的：
`ready-for-agent` 表示已附上简报、应由 agent 处理 diff 的下一步；
`ready-for-human` 表示它已准备好让人合并。

**每个被 triage 过的 issue 应当恰好带一个分类角色和一个状态角色。**
状态角色冲突的话，标出来，先问维护者，再做别的。

这些是**规范角色名**。issue tracker 里实际用的标签字符串可能不同。
映射关系应该已经给你配好了。没有的话，让用户跑 `/setup-matt-pocock-skills`。

**状态转移**：没有标签的 issue 通常先进 `needs-triage`；
从那里可以去 `needs-info`、`ready-for-agent`、`ready-for-human` 或 `wontfix`。
报告人回复后，`needs-info` 回到 `needs-triage`。
**维护者随时可以覆盖**；看起来不寻常的转移，先标出来问一下再动手。

## 调用

维护者敲 `/triage` 并用自然语言描述他想要什么。解读请求并执行。例如：

- "给我看需要我关注的东西"
- "看看 #42"（issue 或 PR）
- "把 #42 移到 ready-for-agent"
- "有什么是 agent 可以领走的？"

## 展示需要关注的东西

查 issue tracker，呈现三个桶，最老的在前：

1. **无标签**：从未 triage 过。
2. **`needs-triage`**：评估进行中。
3. **`needs-info` 且上次 triage 记录之后报告人有活动**：需要重新评估。

PR 在范围内时，把这些外部 PR 也放进这几个桶，并给每一行标上 `[PR]` 或 `[issue]`。
**发现环节只覆盖**外部** PR**（tracker 配置定义了谁算外部），
所以协作者的进行中 PR 不算 triage 工作。
**这个过滤只作用于发现环节**；被明确点名的 PR 无论作者是谁都要 triage。

显示数量，以及每条一行摘要。让维护者挑。

## Triage 一个具体的 issue 或 PR

1. **收集上下文。** 读完整的 issue 或 PR（正文、评论、标签、作者、日期；PR 还要读 diff）。
   解析任何之前的 triage 记录，这样你不会重问已解决的问题。
   用项目的领域术语表探索代码库，尊重那片区域的 ADR。
   对代码库跑两项检查：
   (a) **冗余**：按**领域概念**（不只是请求的措辞）搜索所请求行为是否已有实现，
   并报告你查过哪里。找到了就是"已实现型的 `wontfix`"（见第 5 步）。
   (b) **先前否决**：读 `.out-of-scope/*.md`，把跟本请求相似的都摆出来。

2. **给建议。** 告诉维护者你建议的分类和状态，附上理由，
   以及一份跟该请求相关的简短代码库摘要（包括它是否已被实现）。**等指示。**

3. **验证论断。** 在盘问之前，先确认这个论断站得住。
   bug 就按报告人的步骤复现。
   PR 就确认 diff 做的事跟它声称的一致：checkout 下来，跑相关测试或命令。
   报告结果：已确认（附代码路径）、未能确认、或细节不足（强烈的 `needs-info` 信号）。
   **验证过的结论能让 agent 简报强得多。**

4. **盘问（如果需要）。** 请求需要补全时，用 Skill 工具调用两次：
   `grilling` 和 `domain-modeling`，一轮问题一轮问题地把它盘成型，
   同时磨锋利领域术语，决策落定就就地更新 `CONTEXT.md` / ADR。

5. **施加结果：**
   - `ready-for-agent`：发一条 agent 简报评论（见上游 `AGENT-BRIEF.md`）。
   - `ready-for-human`：结构和 agent 简报一样，
     但注明为什么不能委派（需要判断、需要外部访问、需要设计决策、需要手工测试）。
   - `needs-info`：发 triage 记录（下面的模板）。
   - `wontfix` 就关闭 issue，评论内容取决于**为什么**：
     - **已实现**：改动已经存在于代码库中。指出它在哪；
       **不要**往 `.out-of-scope/` 写（那个知识库是给**被否决**的请求用的，不是给已构建的）。
     - **否决（bug）**：给一个客气的解释，然后关闭。
     - **否决（enhancement）**：写进 `.out-of-scope/`，从评论里链过去，然后关闭。
   - `needs-triage`：施加该角色。有部分进展的话可以留一条可选评论。

## 快速状态覆盖

维护者说"把 #42 移到 ready-for-agent"，就信他，直接施加该角色。
确认你即将做什么（角色变更、评论、关闭），然后动手。**跳过盘问。**
没有经过盘问就移到 `ready-for-agent` 时，问一下他要不要写一份 agent 简报。

## needs-info 模板

```markdown
## Triage Notes

**目前已经确认的：**

- 第 1 点
- 第 2 点

**还需要你（@报告人）提供的：**

- 问题 1
- 问题 2
```

把盘问过程中解决的一切都记到"已经确认的"下面，这样工作不会丢。
**问题必须具体、可执行**，不能是"请提供更多信息"。

## 恢复之前的会话

issue 或 PR 上已有先前的 triage 记录时，读一下，
检查报告人有没有回答任何悬而未决的问题，继续之前先呈现更新后的全貌。
**不要重问已解决的问题。**

> **译者注**：两个设计细节值得抄走：
>
> **1. `needs-info` 模板里的"已经确认的"那一节。**
> 它的作用是防止**盘问成果丢失**——
> 一轮盘问可能花掉几万 token 才把一个问题问清楚，
> 如果只写"还需要你提供 X"，那么下次回来时之前问清的东西全没了。
>
> **2. 第 3 步"先验证论断，再盘问"。**
> 顺序是刻意的。如果是"已经实现了"或者"根本复现不了"，
> 那么后面整套盘问流程都是白做的。
> **先花一分钟证伪，能省掉一小时的访谈。**
>
> 另外 `wontfix` 分三种、并且**只有"否决 enhancement"才写进 `.out-of-scope/`**，
> 这个区分很实用：把"已实现"也记进去会污染那个知识库，
> 让未来的 triage 误以为某个功能被否决过。
