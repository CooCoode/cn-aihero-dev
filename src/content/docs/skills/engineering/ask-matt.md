# 问 Matt

你记不住每一个 skill，所以来问。

**流程（flow）**是穿过这些 skill 的一条路径。
多数路径沿一条**主流程**走，有两条**匝道**汇入它。
其余的不是独立存在，就是在底下运行的词汇层。

## 主流程：想法 → 交付

多数工作走的路线。你有一个想法，想把它建出来。

1. **`/grill-with-docs`** 通过访谈把想法磨锋利。
   **只要你在一个工作目录里工作，就从这里开始**：
它是有状态的，会把学到的东西保留在 `CONTEXT.md` 和 ADR 里。
   （没有工作目录就用 `/grill-me`，见「独立使用」。
   两者跑同一个 `/grilling` 原语；`grill-with-docs` 是留下纸面痕迹的那个，
   所以只要有仓库可以留痕，它就是两者中更好的。）

2. **分支：每个问题都能在对话里定下来吗？**
   如果某个问题需要一个**能跑的答案**（状态、业务逻辑、一个你必须看见的 UI），
   就绕道做个原型，两个方向都用 **`/handoff`** 搭桥
   （原型住在它自己的目录里，而这正是 `/handoff` 的用途）：
   - **`/handoff`** 出去，然后针对那个文件开一个新会话
   - **`/prototype`** 用丢弃型代码回答那个问题
   - **`/handoff`** 把学到的东西带回来，并从原来的想法线程里引用它

3. **分支：这是一个跨会话的构建吗？**
   - **是** → **`/to-spec`**（把线程变成规格），然后 **`/to-tickets`**
     拆成曳光弹工单，每个声明它的**阻塞边**。
     本地 tracker 上就是 `.scratch/<feature>/issues/` 下一个工单一个文件，
     手工按阻塞者优先推进；
     真实 tracker 上阻塞边变成原生 blocking 链接，
     于是任何阻塞者已完成的工单都能被领走：
     每个工单起一个 **`/implement`**，**每个之间 `/clear` 一次上下文**。
     每张工单是自包含的，所以上一张的上下文是可以丢的。
   - **否** → 就在**这里**、同一个上下文窗口里跑 **`/implement`**。

   两种情况下，**`/implement`** 都在内部驱动 **`/tdd`** 来构建每个 issue
   （一次一个红绿切片），然后收尾时跑 **`/code-review`**——
   对 diff 做的双轴（标准 + 规格）审查——再提交。
   当你只想把一个具体行为测试先行地建出来、不需要完整规格时，单独用 **`/tdd`**；
   想对照某个固定点审查一个分支或 PR 时，单独用 **`/code-review`**。

### 上下文卫生

让第 1–3 步待在**一个不间断的上下文窗口**里
（在 `/to-tickets` 之前不要 compact 或 clear），
这样盘问、规格、工单都建立在同一套思考上。
每个 `/implement` 则从零开始，靠工单工作。

这件事的上限是 **smart zone**：
模型仍然推理锐利的那个窗口（前沿模型上约 15 万 token）。
一个会话在 `/to-tickets` 之前逼近它时，**不要在降级状态下硬顶**；
在最接近的阶段边界处 `/compact` 然后继续（见「阶段边界」）。

## 匝道

一种会**生成工作**、然后汇入主流程的起始处境。

- **bug 和请求堆积** → **`/triage`**。
  它让 issue 走过 triage 角色，产出 agent 可用的 issue，之后由 `/implement` 接手。

  **triage 只针对不是你创建的 issue**：bug 报告、外部来的功能请求、
  任何原始到达的东西。
  `/to-tickets` 产出的工单已经是 agent 可用的，所以**不要 triage 它们**。

- **有东西坏了** → **`/diagnosing-bugs`**。
  针对难的那些：看一眼解决不了的 bug、间歇性的 flake、
  在两个已知正确状态之间溜进来的回退。
  在拿到一个**紧的反馈环**（一条已经能在这个 bug 上变红的命令）之前，
  它拒绝建立理论，然后用一个回归测试来修。
  当真正的发现是"没有好缝能把这个 bug 锁住"时，
  它的复盘会交接给 **`/improve-codebase-architecture`**。

- **一大片迷雾中的工作：绿地项目，或者一个会话装不下的巨大功能** → **`/wayfinder`**，
  这里是认知负担最重的流程。
  从这里到目的地的路还看不见时，它在 issue tracker 上画出一张
  **决策工单**的**共享地图**，一次解一个，
  产出**决策而不是交付物**，直到雾被推回去、路清晰。
  `/grill-with-docs` 磨的是一个你能在一个会话里握住的想法，
  wayfinder 是给你握不住的那个，它更慢也更稠密，
  所以**留给确实需要的情况，绝不用于一个范围清楚的功能**。

  地图清晰之后，**它交接，它不构建**：
  在 **`/to-spec`** 处汇入主流程——它把地图里关联的决策压成一份可建的计划，
  然后照常 `/to-tickets` 和 `/implement`。
  把地图直接接进 `/implement` 会跳过那次压缩、丢掉关联的细节，
  所以**只有当这次行动结果确实很小**时才直奔 `/implement`。

## 代码库健康

不是功能工作，只是维护。

- **`/improve-codebase-architecture`** 在你任何有空的时候跑一下，
  让代码库保持适合 agent 操作。它把**加深机会**摆出来；
  挑一个就**生成一个想法**，你可以带着它到主流程的 `/grill-with-docs`。
  它是找出候选的勘察；**`/codebase-design`**（见下）是你设计选中那个的工作台。

## 底下的词汇层

两个由模型自行调用的参考，在别的 skill **底下**运行，
各自是自己那套词汇的唯一真相来源。
**当问题是"词"而不是"流程"时，直接去找它们**；或者让上面的 skill 把它们拉进来。

- **`/domain-modeling`**：磨锋项目**领域**语言——
  挑战一个模糊术语、解决一个一词多义的词（"account" 干了三件事）、
  把难以逆转的决策记成 ADR。
  它是 `/grill-with-docs` 驱动的、让 `CONTEXT.md` 保持为一份干净术语表的那个主动功夫。
- **`/codebase-design`** 是深模块词汇（模块、接口、深度、缝、适配器、杠杆、局部性），
  用来设计一个模块的**形状**：小接口后面藏着大量行为，划在一条干净的缝上。
  `/tdd` 和 `/improve-codebase-architecture` 都说这套语言。

## 阶段边界

一个**阶段（phase）**是会话内部的一块工作：盘问、实现、QA。
在两个阶段的**边界**上你有五个选项，而在它们之间选择是**整张地图里最模糊的一个决策**：

- **Continue（继续）**：原地不动。不花成本，不丢东西。
- **`/clear`**：清空窗口，当这里的东西对接下来都不重要时。
- **`/handoff`** 写一个可携带的 markdown 文件。
  很窄：**只**用于**新承载器**、**新目录**、**同事**，
  或者在阶段**中途**给一个侧任务开叉。它买到的是**可携带性**。
- **Subagent**：把一个范围很紧的任务送到它自己的窗口，拿一份报告回来。
- **`/compact`** 压缩当前上下文，并用它播种一个新会话。
  **默认选项**，在决策树的底部而不是伸手就抓的第一个。

有序的决策树（五个问题、每个分支背后的推理、
以及为什么一手来源的代价让 **Continue** 成为**第一个该被排除**的选项）
见上游 `PHASE-BOUNDARIES.md`。
**在边界上做这个决策**；阶段中途，要么继续，要么把剩下的拆成 subagent。

## 独立使用

完全不在主流程上。

- **`/grill-me`**：跟 `/grill-with-docs` 同样无情的访谈，但**无状态**：
  不往本地存任何东西，也不建 `CONTEXT.md`。
  **不在工作目录里工作时**用它（磨一个计划、一个设计、一篇文字，任何底下没有仓库的东西）。
  在工作目录里就用 `/grill-with-docs`：它跑同样的访谈并留下纸面痕迹，
  所以它是严格更好的那个。
- **`/grilling`** 就是那个访谈原语本身：轮次、前沿、事实是 agent 的活、决策是你的。
  `/grill-me` 和 `/grill-with-docs` 是两个命名的入口，
  而 `/triage`、`/wayfinder`、`/improve-codebase-architecture` 都在内部跑它。
  **只有想要不加包装的访谈本身时**才直接用。
- **`/resolving-merge-conflicts`** 逐 hunk 处理进行中的 merge 或 rebase 冲突，
  按追溯到每一侧**一手来源**的**意图**来解决，而不是挑行，然后完成这次操作。
  它从不跑 `--abort`。独立、不在任何流程上：你已经卡在冲突里时用它。
- **`/prototype`** 是一个小而一次性的程序，回答一个设计问题：
  这个状态模型感觉对吗，或者这个 UI 该长什么样。
  **一次性是关于代码怎么写的一条约束，不是"会摧毁它"的承诺**：
  答案折进真实代码，而原型本身作为**一手来源**保存在从 main 开出的
  `prototype/<名字>` 分支上，从实现 issue 指过去。
  它是主流程第 2 步的那个绕道，但任何时候一个设计问题在纸上定不下来都可以用它。
- **`/research`**：把读资料的腿脚活委派给一个**后台 agent**：
  它针对**一手来源**调查一个问题，然后在仓库里留下一份带引用的 Markdown。
  它读的时候你继续工作。
  它产出的文件是**带进**主流程 `/grill-with-docs` 的东西，
  因为调研喂给思考，而不是替代思考。
- **`/to-questionnaire`** 出现在卡住你的东西既不在你脑子里、
  也不在代码库里，而在**别人**那里时，它给对方写一份问卷去填。
  它是 `/grill-me` 的反面：不访谈你关于**主题**，而是访谈你关于**寄送**
  （寄给谁、要拿回什么），然后把问题瞄准那个缺口。
  拿回来的东西是 `/grill-with-docs` 或 `/to-spec` 的材料。
- **`/wizard`** 是给只有**人**能做的步骤用的：
  配基础设施、配凭据或 CI secrets、在一个不熟悉的第三方控制台里点来点去、
  跑一次性迁移或切换。
  它生成一个交互式 bash 脚本，打开每个 URL、捕获每个值、
  写进 `.env` 和 GitHub secrets，
  让这个过程不再需要每次跟 agent 重新解释一遍。
  由模型自行调用，所以 agent 一撞上只有你能过的墙就会去拿它。
  **agent 自己能做的就该自己做**；这个是给人确实在回路里的地方用的。
- **`/wait-what`** 是对一条没讲清的消息的矫正。
  在对话中途、在任何其他 skill 内部使用，
  agent 就会用你缺的那份上下文、用平实的语言、用 `CONTEXT.md` 的词汇重讲一遍它刚说的话。
  它是事后补救；`/grill-with-docs` 是事先的根治，
  因为早早商定的共享语言才是不让黑话出现的东西。
- **`/teach`**：跨多个会话学一个概念，把当前目录当有状态的工作区用。
- **`/writing-for-agents`** 是写 agent 消费的文档的参考：skill、AGENTS.md、被指针引到的文档。

## 前置条件

**`/setup-matt-pocock-skills`**：在第一次跑工程流程之前运行，
配置其他 skill 所假设的 issue tracker、triage 标签和文档布局。自定义 issue tracker 也能用。

> **译者注**：**如果你只想读一个页面，读这个。** 它是整套方法论的目录页。
>
> 三个值得注意的设计：
>
> **1. 上下文卫生那一节。** 它说第 1–3 步（盘问 → 规格 → 工单）
> 要待在**一个不间断的窗口**里，然后每个 `/implement` 才从零开始。
> 理由很实在：盘问、规格、拆工单**是同一次思考的三个阶段**，
> 中间 compact 一次就等于把推理链切断。
> 而实现阶段是自包含的，所以那里的上下文可以丢。
>
> **2. "smart zone"（约 15 万 token）。** 超过它模型就开始降级，
> 这时候该做的是**在最近的阶段边界处 compact**，
> 而不是"再顶一下"。
>
> **3. 阶段边界那五个选项，默认值是 `/compact` 而不是 `/clear`。**
> 顺序是 Continue → clear → handoff → subagent → compact，
> 但注意它说 `/compact` 是**默认**、是"决策树底部而不是伸手就抓的第一个"——
> 意思是**先认真考虑前面几个**，只有它们都不合适才压缩。
> 因为 compact 会**有损**，而 clear 和 handoff 不会。

## 安装

**斜杠命令入口**（`disable-model-invocation: true`）：agent 不会自己调用它，只有你敲命令才触发。`description` 也译成中英双语——它只是命令面板里的说明，翻译对中文用户更友好，保留英文便于对照。

```yaml
---
name: ask-matt
description: "不确定该用哪个 skill 或流程时问它。Ask which skill or flow fits your situation."
disable-model-invocation: true
---
```
