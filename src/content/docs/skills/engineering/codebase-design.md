设计**深模块（deep module）**：**小接口后面藏着大量行为**，划在一条干净的**缝**上，通过那个接口可测。
凡是设计或重构代码的地方，都用这套语言和原则。
目标是：给调用方**杠杆**，给维护者**局部性**，给所有人**可测性**。

## 术语表

**严格使用这些词**：不要替换成"组件""服务""API""边界"。**用词一致本身就是重点。**

**模块（Module）**：任何有接口和实现的东西。刻意做成**尺度无关**：
一个函数、一个类、一个包，或者一个横跨多层的切片。
_避免用_：单元、组件、服务。

**接口（Interface）**：调用方要正确使用这个模块**必须知道的全部事实**：
类型签名，也包括不变量、顺序约束、错误模式、必需配置、性能特征。
_避免用_：API、签名（太窄了，它们只指类型层面的表面）。

**实现（Implementation）**：模块里面是什么，它的代码主体。
与**适配器（Adapter）**区分：一个东西可以是很小的适配器配很大的实现（一个 Postgres 仓储），
也可以是很大的适配器配很小的实现（一个内存版假实现）。
**话题是缝的时候用"适配器"，否则用"实现"。**

**深度（Depth）**：接口处的**杠杆**。
调用方（或测试）每学一单位接口，能驱动多少行为。
一个模块**深**，是指大量行为藏在一个小接口后面；
**浅**，是指接口几乎和实现一样复杂。

**缝（Seam）** _(Michael Feathers)_：一个你能**不修改该处代码就改变其行为**的地方；
**模块接口所在的那个位置**。缝放在哪是独立的设计决策，跟缝后面放什么不是一回事。
_避免用_：边界（boundary，跟 DDD 的限界上下文 bounded context 撞车）。

**适配器（Adapter）**：在一条缝上满足某个接口的具体东西。
描述的是**角色**（它填哪个槽），不是实质（里面是什么）。

**杠杆（Leverage）**：调用方从深度里得到的东西。每学一单位接口，多得到一点能力。
一份实现，在 N 个调用点和 M 个测试上回本。

**局部性（Locality）**：维护者从深度里得到的东西。
变更、bug、知识、验证都集中在一处，而不是散在调用方之间。**一处修好，处处修好。**

## 深 vs 浅

**深模块** = 小接口 + 大量实现：

```
┌─────────────────────┐
│      小接口          │  ← 方法少，参数简单
├─────────────────────┤
│                     │
│      深的实现        │  ← 复杂逻辑藏在里面
│                     │
└─────────────────────┘
```

**浅模块** = 大接口 + 几乎没有实现（要避免）：

```
┌─────────────────────────────────┐
│            大接口                │  ← 方法多，参数复杂
├─────────────────────────────────┤
│        薄薄的实现                │  ← 纯转发
└─────────────────────────────────┘
```

设计接口时问自己：

- 方法数量能减少吗？
- 参数能简化吗？
- 能藏更多复杂度到里面吗？

## 原则

- **深度是接口的属性，不是实现的属性。**
  一个深模块内部可以由小的、可 mock 的、可替换的零件组成；它们只是不属于接口的一部分。
  一个模块可以有**内部缝**（对其实现私有，供它自己的测试用），
  也可以有接口处的**外部缝**。
- **删除测试（The deletion test）。** 想象把这个模块删掉。
  如果复杂度消失了，说明它只是一个转发管道。
  如果复杂度在 N 个调用方那里重新冒出来，说明它挣到了自己的位置。
- **接口就是测试面。** 调用方和测试走的是同一条缝。
  如果你想要**绕过**接口去测，说明这个模块形状大概率不对。
- **一个适配器意味着假想的缝，两个适配器才意味着真实的缝。**
  除非真的有东西跨着缝在变，否则不要引入缝。

## 为可测性而设计

好接口让测试自然发生：

1. **接受依赖，不要创建依赖。**

   ```typescript
   // 可测
   function processOrder(order, paymentGateway) {}

   // 难测
   function processOrder(order) {
     const gateway = new StripeGateway();
   }
   ```

2. **返回结果，不要产生副作用。**

   ```typescript
   // 可测
   function calculateDiscount(cart): Discount {}

   // 难测
   function applyDiscount(cart): void {
     cart.total -= discount;
   }
   ```

3. **表面积要小。** 方法少 = 需要的测试少。参数少 = 测试准备简单。

## 概念之间的关系

- 一个**模块**恰好有一个**接口**（它呈现给调用方和测试的表面）。
- **深度**是**模块**的属性，相对于它的**接口**来度量。
- **缝**是**模块**的**接口**所在的位置。
- **适配器**坐在**缝**上，满足**接口**。
- **深度**为调用方产生**杠杆**，为维护者产生**局部性**。

## 被否决的几种说法

- **深度 = 实现行数与接口行数之比**（Ousterhout）：这会奖励往实现里灌水。
  我们用**深度即杠杆**。
- **"接口" = TypeScript 的 `interface` 关键字或类的公开方法**：太窄。
  这里的接口包含调用方必须知道的每一个事实。
- **"边界"**：跟 DDD 的限界上下文撞车。请说**缝**或**接口**。
