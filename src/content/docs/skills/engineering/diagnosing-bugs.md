# 诊断 Bug

一套对付硬骨头 bug 的纪律。**除非有明确理由，否则不要跳过任何阶段。**

探索代码库时，读 `CONTEXT.md`（如果存在）拿到相关模块的清晰心智模型，
并检查你正在触碰那片区域的 ADR。

## 抹除敏感信息

本 skill 会让你展示命令、输出和捕获的产物。
**先把每一个密钥抹掉**：用 `<REDACTED>` 占位。
让循环跑在环境变量上，这样凭据留在环境里，而不是留在你展示的东西里。
捕获的产物会带 auth header：只引用携带信号的那几行。

**如果抹除之后的信息不足以诊断，就说出来并向用户索取。**

## 阶段 1：造一个反馈环

**这个阶段就是整个 skill。** 其余都是机械劳动。
如果你对 bug 有一个**紧（tight）**的通过/失败信号（它会在**这个** bug 上变红），
你一定能找到原因；二分、假设检验、埋点都只是在消费它。
**如果你没有这个信号，盯着代码看多久都救不了你。**

在这里投入不成比例的精力。**要凶。要野。不许放弃。**

### 造环的办法，大致按这个顺序

1. **失败的测试**，在任何一个能触达该 bug 的缝上：单元、集成、e2e。
2. **Curl / HTTP 脚本**，打向跑着的 dev server。
3. **CLI 调用**，喂一个 fixture 输入，把 stdout 跟已知正确的快照 diff。
4. **无头浏览器脚本**（Playwright / Puppeteer），驱动 UI 并断言 DOM / console / network。
5. **回放捕获的 trace。** 把真实的网络请求 / payload / 事件日志存到磁盘，隔离地重放进代码路径。
6. **丢弃型承载器。** 起一个最小子系统（一个服务、mock 掉依赖），用一次函数调用走进 bug 的代码路径。
7. **属性 / 模糊测试循环。** 如果 bug 是"有时输出错"，跑 1000 个随机输入找失败模式。
8. **二分承载器。** bug 出现在两个已知状态之间（commit、数据集、版本）时，
   把"在状态 X 启动、检查、重复"自动化，好让你 `git bisect run` 它。
9. **差分循环。** 同一个输入跑老版本 vs 新版本（或两套配置），diff 输出。
10. **HITL bash 脚本。** 最后手段。如果必须由人点击，
    就用 `scripts/hitl-loop.template.sh` 去驱动**那个人**，让循环依然有结构。
    捕获的输出回流给你。

**造对了反馈环，bug 就已经修好 90%。**

### 把环拧紧

**把环当作一个产品对待。** 有了**一个**环之后，就要**拧紧**它：

- 能让它更快吗？（缓存准备、跳过无关初始化、缩小测试范围。）
- 能让信号更锋利吗？（断言具体的症状，而不是"没崩"。）
- 能让它更确定吗？（锁住时间、给 RNG 定种子、隔离文件系统、冻结网络。）

**一个 30 秒的 flaky 环几乎不比没有环强；一个 2 秒的确定性环是紧的，是调试超能力。**

### 非确定性 bug

目标不是干净的复现，而是**更高的复现率**。
把触发器循环 100 次、并行化、加压、收窄时间窗口、注入 sleep。
**一个 50% 概率 flaky 的 bug 是可调试的；1% 的不是**，
所以持续提高复现率，直到它能被调试。

### 当你真的造不出环

**停下来，明确说出来。** 列出你试过什么。
向用户要：(a) 能复现它的那个环境的访问权，
(b) 一份抹除过的捕获产物（HAR 文件、日志 dump、core dump、带时间戳的录屏），
或 (c) 加入临时生产环境埋点的许可。
**没有环，就不要进入假设阶段。**

### 完成条件：一个紧的、能变红的环

阶段 1 完成的标志是环**紧**且**能变红**：
你能说出**一条命令**（脚本路径、测试调用、curl），你**已经至少跑过一次**
（展示调用和它的输出，已抹除），并且它满足：

- [ ] **能变红**：它驱动**真正的** bug 代码路径并断言**用户的原话症状**，
      所以它能在这个 bug 上变红、修好后变绿。
      不是"跑起来不报错"；它必须**能抓住这个具体的 bug**。
- [ ] **确定性**：每次跑结论一致（flaky bug 见上文，用锁定的高复现率）。
- [ ] **快**：秒级，不是分钟级。
- [ ] **agent 可运行**：你能无人值守地跑它；人在回路只通过 `scripts/hitl-loop.template.sh`。

如果你发现自己在这条命令存在之前就开始读代码建理论，
**停下：直接跳到假设，正是这个 skill 要防的那种失败。没有能变红的命令，就没有阶段 2。**

## 阶段 2：复现 + 最小化

跑环。看着它变红，bug 出现。

确认：

- [ ] 环产出的是**用户**描述的那个失败模式，而不是碰巧在附近的另一个失败。**错的 bug = 错的修复。**
- [ ] 失败在多次运行中可复现（非确定性的 bug 则是复现率足够高到可调试）。
- [ ] 你捕获了确切的症状（错误消息、错误输出、慢的耗时），
      这样后面的阶段能验证修复是否真的解决了它。

### 最小化

红了之后，把复现缩到**仍然变红的最小场景**。
**一次一个**地砍掉输入、调用方、配置、数据、步骤，
每砍一刀重跑一次环，只留下对失败**承重**的东西。

为什么要费这个劲：最小复现缩小了阶段 3 的假设空间（剩下的活动部件更少），
并且它就是阶段 5 里那份干净的回归测试。

完成条件是**剩下的每个元素都承重**：去掉任何一个，环都变绿。

**在复现**并且**最小化**之前，不要往下走。**

## 阶段 3：假设

在测试任何一个之前，先产出 **3–5 个排好序的假设**。
只生成一个假设会锚定在第一个看起来合理的主意上。

每个假设必须**可被证伪**：说清它做出的预测。

> 格式："如果 <X> 是原因，那么 <改 Y> 会让 bug 消失 / <改 Z> 会让它更严重。"

**说不清预测，这个假设就是感觉**：丢掉，或者磨锋利。

**测试之前把排序后的列表给用户看。**
他们常有领域知识能瞬间重排（"我们刚给 #3 部署了一个改动"），
或者知道他们已经排除掉的假设。**这是个便宜得多的检查点，能省大量时间。**
不要因此阻塞；用户不在就按你的排序继续。

## 阶段 4：埋点

**每个探针都要映射到阶段 3 里一个具体的预测。一次只改一个变量。**

工具偏好：

1. **调试器 / REPL 查看**，如果环境支持。**一个断点胜过十条日志。**
2. **有针对性的日志**，打在区分假设的那些边界上。
3. **绝不"全都打日志然后 grep"。**

**给每条调试日志打上唯一前缀**，例如 `[DEBUG-a4f2]`。
最后清理就变成一次 grep。**没打标签的日志会活下来；打了标签的会死。**

**性能分支。** 对性能回退，日志通常是错的做法。
改为：先建立基线测量（计时承载器、`performance.now()`、profiler、查询计划），然后再二分。
**先测量，再修。**

## 阶段 5：修复 + 回归测试

**在修复之前**写回归测试，但**只有存在正确的缝时**才这么做。

正确的缝，是指测试能演练**调用点实际发生的那种真实 bug 模式**。
如果可用的缝太浅（bug 需要多个调用方，却只能写单调用方测试；
单元测试无法复制触发 bug 的那条链），在那里写回归测试只会给出**虚假的信心**。

**如果不存在正确的缝，这本身就是发现。** 记下来。
**代码库的架构正在阻止这个 bug 被锁死。** 把它标给下一个阶段。

存在正确的缝的话：

1. 把最小复现变成该缝上的一个失败测试。
2. 看着它失败。
3. 施加修复。
4. 看着它通过。
5. 拿阶段 1 的反馈环重跑原始的（未最小化的）场景。

## 阶段 6：清理

宣布完成之前必须做到：

- [ ] 原始复现不再复现（重跑阶段 1 的环）
- [ ] 回归测试通过（或者"缺缝"这件事已被记录在案）
- [ ] 所有 `[DEBUG-...]` 埋点已移除（用前缀 `grep` 一遍）
- [ ] 丢弃型原型已删除（或移到明确标记的 debug 位置）
- [ ] 最终正确的那个假设写进了 commit / PR 消息，好让下一个调试者学到东西

> **译者注**：这个 skill 值得第一次就完整读一遍，因为它跟大多数人的调试本能相反。
>
> 最大的反直觉点是：**"先读代码建理论"是它要防的失败**。
> 人的本能是看代码、猜原因、改一行试试。
> 而这里要求你先花大力气造一个**能自动跑、能变红、两秒出结果**的命令。
>
> 为什么？因为一旦有了这个命令，**二分、假设、埋点全部变成廉价操作**——
> 每次试一个想法只要两秒。而没有它，每次验证想法都要手工操作五分钟，
> 于是你会退化成"凭直觉改代码"，改十次中一次。
>
> 另外两个细节很实用：`[DEBUG-a4f2]` 这种**标签化日志**让清理变成一次 grep；
> 而"**没有正确的缝，这本身就是发现**"把测试写不出来这件事，
> 从失败提升成了架构信号。
