# 改进代码库架构

把架构摩擦暴露出来，并提出**加深机会（deepening opportunities）**：
把浅模块变成深模块的重构。目标是**可测性**和 **AI 可导航性**。

这个命令**受**项目领域模型**启发**，并建立在共享的设计词汇上：

- 用 Skill 工具调用 `codebase-design` 拿架构词汇
  （**模块**、**接口**、**深度**、**缝**、**适配器**、**杠杆**、**局部性**）
  及其原则（删除测试、"接口就是测试面"、"一个适配器 = 假想的缝，两个 = 真实的"）。
  **每条建议都严格使用这些词**，不要飘到"组件""服务""API""边界"上去。
- `CONTEXT.md` 里的领域语言为好缝提供名字；
  `docs/adr/` 里的 ADR 记录了**本命令不该重新翻案**的决策。

## 流程

### 1. 探索

**扫之前先界定范围：YAGNI。**
加深一个模块的回报是让**未来对它的改动**更容易，
所以**给最近改动过的部分更大权重**。看之前先决定**看哪**：

- 用户点了方向（某个模块、某个子系统、某个痛点）就听他的，跳过后面的推断。
- 否则往回翻一段像样的提交历史（`git log --oneline`）找出代码库的**热点**，
  即反复出现的文件和区域，让这些路径先吸引你的注意。
  如果改动分散、没有明显热点，就撒开网。

先读项目的领域术语表（`CONTEXT.md`）和你正在触碰那片区域的 ADR。

然后派一个 subagent 走一遍代码库。
**不要遵循死板的启发式**；有机地探索，并记下你**亲身遇到摩擦**的地方：

- 哪里理解一个概念需要在很多小模块之间跳来跳去？
- 哪里的模块是**浅**的，接口几乎和实现一样复杂？
- 哪里纯粹为了可测性抽出了纯函数，但真正的 bug 藏在它们的**调用方式**里（没有**局部性**）？
- 哪里紧耦合的模块从缝里漏了出来？
- 代码库的哪些部分没有测试，或者**通过它们当前的接口很难测**？

对你怀疑是浅的东西应用**删除测试**：删掉它是会**集中**复杂度，还是只是把它**挪走**？
"是的，会集中"就是你要的信号。

### 2. 把候选做成 HTML 报告

写一个自包含的 HTML 文件到操作系统临时目录，**别让任何东西落进仓库**。
从 `$TMPDIR` 解析临时目录，退回 `/tmp`（Windows 上是 `%TEMP%`），
写到 `<tmpdir>/architecture-review-<时间戳>.html`，让每次跑都是新文件。
替用户打开它（Linux `xdg-open <路径>`、macOS `open <路径>`、Windows `start <路径>`），
并告诉他们绝对路径。

报告用 **CDN 版 Tailwind** 做布局和样式，
用 **CDN 版 Mermaid** 画那些用图/流/时序能可靠传达结构的图。
**把 Mermaid 和手写的 CSS/SVG 视觉混着用**：
关系是图状的（调用图、依赖、时序）就用 Mermaid；
想要更社论化的东西（质量图、剖面图、折叠动画）就用手搭的 div/SVG。
每个候选都要有**改前/改后可视化**。**要视觉化。**

每个候选渲染一张卡片，包含：

- **文件**：涉及哪些文件/模块
- **问题**：当前架构为什么在制造摩擦
- **解法**：用大白话说会改什么
- **收益**：用局部性和杠杆来解释，以及测试会怎么改善
- **改前 / 改后图**：并排、手绘，示意"浅"和"加深"
- **推荐强度**：`强`、`值得探索`、`投机` 三者之一，做成徽章

报告结尾放一节 **首选推荐**：你会先动哪个候选，为什么。

**领域用 CONTEXT.md 的词汇，架构用 `/codebase-design` 的词汇。**
如果 `CONTEXT.md` 定义了 "Order"，就说"Order 接收模块"，
**不要说 "FooBarHandler"，也不要说 "Order 服务"。**

**ADR 冲突**：候选跟已有 ADR 矛盾时，
**只有当摩擦真实到值得重开那个 ADR 时**才提出来。
在卡片里明确标出（例如一个警告框：_"与 ADR-0007 矛盾，但值得重开，因为……"_）。
**不要把 ADR 理论上禁止的每一个重构都列一遍。**

完整的 HTML 骨架、图表模式和样式指导见上游 `HTML-REPORT.md`。

**先不要提接口。** 文件写完之后问用户："你想深入探索哪一个？"

### 3. 盘问循环

用户选中一个候选后，用 Skill 工具调用 `grilling`，跟他一起走决策树：
约束、依赖、加深后模块的形状、缝后面坐着什么、哪些测试能活下来。

决策一凝固就地产生副作用；过程中用 Skill 工具调用 `domain-modeling` 让领域模型保持最新：

- **用 `CONTEXT.md` 里没有的概念给加深后的模块命名？** 把术语加进 `CONTEXT.md`。
  文件不存在就懒创建。
- **对话中磨锋利了一个模糊术语？** 就地更新 `CONTEXT.md`。
- **用户带着承重理由否决了这个候选？** 提议写个 ADR，措辞是：
  _"要不要我把它记成一个 ADR，好让未来的架构评审不再重提它？"_
  **只有当这个理由确实是未来的探索者避免重提同一件事所必需的**才提议；
  跳过短暂的理由（"现在不值得"）和不言自明的理由。
- **想探索加深后模块的替代接口？** 用 Skill 工具调用 `codebase-design`，
  用它的 design-it-twice 并行 subagent 模式。
