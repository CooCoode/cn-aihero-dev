# 原型

原型是**回答一个问题、用完即扔的代码**。**问题决定形状。**

## 先选分支

判断正在回答的是哪个问题，依据用户的提示词、周围的代码，或者趁用户在的时候直接问：

- **"这段逻辑 / 状态模型感觉对吗？"** → `LOGIC.md` 分支。
  做一个**单个可分享的 HTML 文件**（自由操作按钮 + 分标签页的引导式走查），
  把状态机推过那些在纸上很难想清楚的场景，而且**非开发者也能操作**。
- **"这东西应该长什么样？"** → `UI.md` 分支。
  在**同一个路由**上生成几个**截然不同**的 UI 变体，用 URL search param 加底部浮动条切换。

两个分支产出的东西差别极大，**选错就浪费掉整个原型**。
问题确实含糊、又联系不上用户时，默认选更贴合周围代码的那个分支
（后端模块 → 逻辑；页面或组件 → UI），并在原型顶部**写明这个假设**。

## 两个分支都适用的规则

1. **从第一天就是丢弃品，并且明确标出来。**
   把原型代码放在它真正会被用到的位置附近（就在它所原型化的模块或页面旁边），
   上下文才明显；但**命名要让随手看到的人一眼认出这是原型，不是生产代码**。
   丢弃型 UI 路由要遵守项目已有的路由约定；不要发明新的顶层结构。
2. **跑起来要毫无成本。** UI 原型从项目的任务运行器一条命令启动：
   `pnpm <name>`、`python <path>`、`bun <path>` 等。
   逻辑 demo 是用户**双击就能开的一个 HTML 文件**。总之，启动不需要动脑子。
3. **默认不持久化。** 状态放内存里。
   **持久化是原型要检查的东西，不是它该依赖的东西。**
   如果问题明确涉及数据库，就打一个草稿库或者一个名字明确写着"PROTOTYPE, wipe me"的本地文件。
4. **跳过打磨。** 不写测试，错误处理只做到让原型**能跑**为止，不做抽象。
   重点是**快速学到东西**。
5. **把状态摊出来。** 每次操作后（逻辑），或每次切换变体时（UI），
   打印或渲染出完整的相关状态，让用户看见到底变了什么。
6. **做完就归档。** 把验证过的决策折回真实代码，然后把原型本身作为**一手来源**归档：
   提交到一个丢弃型分支（不进 main），并在实现 issue 上留一个指向该分支的
   context pointer。**同时把答案也记下来**（结论，以及它解决了哪个问题）
   写进 issue 或 commit。**main 上只保留那个验证过的决策。**

> **译者注**：第 2 条和第 6 条是这里最容易被忽略、也最值钱的两条。
>
> **"双击就能开"** —— 原型的唯一目的是**快速学到东西**。
> 如果为了看效果要先装依赖、配环境、跑迁移，学习成本就已经超过学习收益了。
>
> **"归档成一手来源"** —— 原型扔了，但**结论不能扔**。
> 三个月后有人问"为什么状态机是这样设计的"，答案在那个丢弃分支的 commit 里。
> 这是把一次性探索变成可追溯决策的关键一步。
